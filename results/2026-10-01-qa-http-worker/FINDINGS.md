# 面向实际使用的结论

本次完成 **3 轮、168 次完整 HTTP 请求**：144 次自然回答、24 次固定 64 token 控制。六道独立题、两种资料长度、四种配置；不是 144 道独立能力评测题。全部请求走检索、分词、模型生成、KV cache、解码和流式响应。[统计表与原始数据](README.md)

## 用户真正能感受到多少变化

短资料为检索出的两篇文档，约 370–403 输入 token；长资料为全部六篇，约 979–991 输入 token。下表是自然回答请求的中位数。

| 改动 | 短资料整段回答 | 长资料整段回答 | 如何解读 |
|---|---:|---:|---|
| CPU FP32 → GPU BF16 eager | 10.512 → 0.768 秒 | 19.827 → 0.948 秒 | 本机有明显体验收益；同时更换了设备和精度，不能算作注意力优化的收益 |
| GPU BF16 eager → SDPA auto | 0.768 → 0.846 秒 | 0.948 → 1.020 秒 | 本批自然回答没有变快；不同实现也会改变答案长度 |
| GPU BF16 eager → 强制 cuDNN | 0.768 → 2.564 秒 | 0.948 → 1.274 秒 | 在这个变长 KV-cache 服务中，更换后端反而增加等待 |

短资料首段文字等待，CPU FP32 为 **5.117 秒**，GPU BF16 eager 为 **0.050 秒**。这些是已启动、预热后服务的本机 HTTP 时间，不含下载、加载、公网延迟或浏览器绘制。

为控制回答长短，固定生成 64 token 时：

- 短资料 eager **2.471 秒**、SDPA **2.384 秒**，两个中位数相差约 **3.5%**。
- 长资料 eager **2.614 秒**、SDPA **2.594 秒**，两个中位数相差约 **0.8%**。
- 配对轮次中既有变快也有变慢，只有三次固定长度样本；这不足以说明存在稳定、显著的应用加速。
- 强制 cuDNN 分别需要 **15.081 / 9.852 秒**。新的 KV 长度仍有很大的初始化成本，不能把固定形状算子预热后的速度直接套到变长生成上。

因此，这个应用目前值得采用的基础方案是 **GPU + BF16 + 只检索相关资料 + 固定推理线程**。本次数据不支持为了明显提速而把默认应用强制改成 cuDNN。普通 eager 与自动 SDPA 均可运行，二者的具体取舍应在自己的模型、问题长度和输出要求下复测。

## 为什么算子结果没有直接变成应用收益

1. 真正回答问题还要运行全部模型层、缓存更新、分词和传输。原来的随机单层注意力结果只覆盖其中一部分。
2. Qwen 使用 GQA，形状与之前测过的随机四头注意力不同。[后端检查](backend_inspection.json)在长资料价格题的前四步生成中记录到：SDPA auto 的 112 次调用全部落到 `aten::_scaled_dot_product_attention_math`；强制配置对应 112 次 cuDNN 调用。这里记录的是 CPU 派发器事件；本机 CUPTI 初始化失败，未获得 CUDA kernel 时间线。
3. 后端初始化和缓存是否复用会影响整个服务。把每个 HTTP 请求新建推理线程改为固定推理线程后，预检中已预热的价格题从约 6–7 秒降到约 0.7 秒；第一次遇到新的长度仍可能慢。该预检是结构诊断，不与正式三轮统计混合。
4. cuDNN 在长资料自然回答中的请求显存增量从 eager 的约 **159 MiB** 降到 **90 MiB**，但含模型的总 allocator 峰值只从约 **3114 MiB** 降到 **3045 MiB**。不能把临时张量节省比例当成整个应用的显存节省比例。

## 答案质量：不能只看速度

已逐条检查全部 **18 种不同的自然回答文本**，覆盖 144 次自然回答。五道有答案题的价格、退款条件、保留时间、导出限制和客服时间均符合文档。短资料下，六题均通过；长资料下，每种配置的无答案题均失败，因此为 **5/6**。

错误非常具体：问“企业定制版年度价格”，资料并没有提供答案。短资料时回答“文档未提供”；长资料时 CPU FP32、SDPA、cuDNN 编造“99 元”，eager BF16 编造“199 元”。这不是 INT8 特有问题，也没有靠更快的后端解决。[完整回答](answers.md)

这次复核由执行实验的助手完成，不是独立人工业务验收或标准能力评分。六道题太少，不能据此保证真实客服准确率；演示不能直接当作经过业务验收的客服上线。

CPU 全 Linear 动态 INT8、仅 MLP INT8、MLP 逐通道 INT8，在更早的价格题预检中就明显跑题，因此被排除出正式候选。FP16 eager 的无效 logits 也已被新的运行时检查实际拒绝。[失败证据](../2026-10-01-qa-preflight/README.md)

## 这两个实验现在的应用价值

它们已经能用于**部署方案筛选与回归验收**：在目标电脑上测用户等待时间，核对实际答案，找出不值得切换的后端和不可接受的量化方案。此次也得到了一项可复用的服务改动——固定推理线程，减少重复初始化。

对于这套具体演示，主要可见收益来自 GPU 运行及服务结构；单换注意力没有得到明显、稳定的收益，简单动态 INT8 则没有通过答案质量关。它们提供了实际选择依据，也阻止把单层的“快若干倍”错误宣传成整个问答工具的提速。
